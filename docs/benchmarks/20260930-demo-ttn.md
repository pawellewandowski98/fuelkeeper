# Teratestnet Demo — Not Run — 2026-09-30

**No funded teratestnet environment was available for this release.**
`cmd/fueldemo` (raw and toolbox modes) was not run against a live arcade or
teranode instance; nothing in this page is a measurement. It records the
exact procedure to run it once a funded teratestnet treasury key and a
reachable arcade/chaintracks pair are available, so the run can be
reproduced without re-deriving the steps from `docs/TREASURY.md` and
`cmd/fueldemo`'s flags.

See [`../TREASURY.md`](../TREASURY.md)'s "Teratestnet Smoke" section for the
narrower `go test -tags ttn` wiring check this demo builds on (one 5-output
split, one keeper round) — that smoke test has also not been run, for the
same reason (see the empty "Verified on Teratestnet" table there); this demo
goes further, driving sustained concurrent reserve/spend traffic through a
running `fuelkeeper serve` instance and a real arcade broadcast.

## Prerequisites

- A funded teratestnet treasury key (`FK_TTN_ROOT_KEY`, 64 hex chars) with
  enough balance to mint FuelKeeper's pool and fund the toolbox wallet used
  in toolbox mode. Fund it with `fuelkeeper fund --sats N`
  ([`../FUNDING.md`](../FUNDING.md)) against a `fuelkeeper serve` running
  `examples/teratestnet.yaml`.
- A reachable arcade instance (`$ARCADE_URL`, e.g.
  `https://arcade-v2-ttn-us-1.bsvblockchain.tech`) and, for toolbox mode, a
  chaintracks instance (`$CHAINTRACKS_URL`, default `<arcade
  host>/chaintracks`).
- `fuelkeeper serve --config examples/teratestnet.yaml` running and reachable
  at `$FUELKEEPER_URL`, with `treasury.kind: toolbox`,
  `FUELKEEPER_TREASURY_KEY=$FK_TTN_ROOT_KEY`, `oracle.kind` left to its
  toolbox-treasury default (`arcade`), and `jobs.enabled: true` so the pool
  actually mints and confirms splits against the real chain.

## Procedure

### 1. Raw mode (Plan 6 Task 4): FuelKeeper's own ceiling

One process, each fuel output spent into its own OP_RETURN transaction
submitted directly to arcade in extended format (no BEEF needed) — the
cheapest possible transaction that still exercises a real reserve, a real
broadcast, and a real spend report back to FuelKeeper:

```bash
fueldemo --mode raw \
  --url "$FUELKEEPER_URL" --key "$FUELKEEPER_API_KEY" --pool main \
  --arcade "$ARCADE_URL" \
  --workers 32 --batch 50 --duration 120s \
  --out docs/benchmarks/results/demo-ttn-raw.json
```

### 2. Toolbox mode (Plan 6 Task 5): a real integrator's path

Four separate `fueldemo` processes, each with 16 workers (128 total
concurrent workers across the four), driving a go-sdk wallet's
`createAction` over reserved fuel inputs — funding itself, broadcasting
through arcade, and verifying every input's BEEF against chaintracks the way
a real integrator would:

```bash
for i in 1 2 3 4; do
  fueldemo --mode toolbox \
    --url "$FUELKEEPER_URL" --key "$FUELKEEPER_API_KEY" --pool main \
    --arcade "$ARCADE_URL" --chaintracks "$CHAINTRACKS_URL" \
    --network ttn --wallet-key "$FUELDEMO_WALLET_KEY_$i" \
    --storage "fueldemo-$i.sqlite" \
    --workers 16 --batch 50 --duration 120s \
    --out "docs/benchmarks/results/demo-ttn-toolbox-$i.json" &
done
wait
```

Each process needs its own `--wallet-key` (a distinct funded key per
process — they must not share a wallet database or a key, or their own
`createAction` calls race each other) and its own `--storage` path.

## What to record

- **Arcade acceptance and 4xx codes**: `fueldemo`'s own JSON report
  (`report.go`) tallies `Sent` (successful build+submit+report round trips)
  against `Failed` by code (e.g. `arcade:backpressure`,
  `reserve:exhausted`, `spend:insufficient`) — record the full `Failed` map
  per run, and separately call out any arcade 4xx (rejected transaction,
  policy violation) vs. 5xx/timeout (arcade backpressure or unavailability)
  since they indicate different problems (a 4xx means FuelKeeper or
  fueldemo built an invalid/policy-violating transaction; a 5xx/timeout
  means arcade itself was saturated or unreachable).
- **Block heights**: chaintracks' (or arcade's) reported tip height
  immediately before the run starts and immediately after it ends, so a
  reviewer can tell how many blocks were mined during the run (relevant to
  how many splits had a chance to confirm, and to the watcher's
  `rebroadcast_after`/`alert_after` windows).
- **FuelKeeper stats before/after** (`GET /v1/pools`, `stats` block):
  `available`, `spent`, `quarantined` at the start and end of each run
  (raw and each toolbox process), so the pool's net drain and the
  reaper/minter's ability to keep up under real chain latency (not the mock
  treasury's fixed `confirm_after`) can be read directly off the deltas.
- **`fuelkeeper_cas_missed_total`** (`/metrics`): should stay at 0 (or
  explain any nonzero reading before publishing the run) — see
  [`../PERFORMANCE.md`](../PERFORMANCE.md)'s audit statement; a nonzero
  reading under real concurrent toolbox-mode load is exactly the scenario
  the G1 invariant test (`pkg/pool/invariant_test.go`'s
  `TestInvariantsConcurrentClients`) exists to catch in CI before it is ever
  seen live.
- **Reserve latency p99** (`fuelkeeper_reserve_latency_seconds` histogram,
  or `fueldemo`'s own `P99Ms` if it is extended to also time the Reserve
  call separately from build+submit): compare against the nullnet numbers in
  [`20260930-api-single.md`](20260930-api-single.md) — teratestnet p99
  should be close to the mock-oracle numbers, since `oracle.kind: arcade`'s
  spend/release verification is `trust`-policy by default for an
  arcade-only oracle (see `docs/OPERATIONS.md`'s "Oracle Kinds and
  Policies") and does not sit in the Reserve path itself.
